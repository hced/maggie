# SPEC.md: Maggie – Technical & Functional Specification

## 1. Project Overview & Scope
**Maggie** is a native Wayland screen magnifier and utility tool written in **Rust (Edition 2024)**. It is designed to run seamlessly on minimal desktop environments and tiling window managers (such as **Niri**) without relying on legacy X11 layers or fallback architectures.

---

## 2. Core Architecture & Environment
* **Language:** Rust (Edition 2024)
* **Display Server Protocol:** Native Wayland exclusively.
* **Task Management:** Managed via a project root `Justfile` (e.g., `just build`, `just run`, `just check`, `just test`).
* **GPU Acceleration:** Rendering is GPU-accelerated via **EGL + OpenGL ES 2** (`src/gpu.rs`): the frozen frame and OSD legend are drawn as textured quads and presented through a `wl_egl_window` at a 2× buffer scale. If EGL/GLES initialization fails, the app **automatically falls back to the CPU rendering path** (`src/render.rs`), which remains fully functional; the choice is made once at startup.

## 3. Screen Capture & Modes — *Implemented*
* **Frozen-frame model:** The screen is captured exactly **once** at startup via `zwlr_screencopy` (`capture_output` on the current output). The SHM buffer (XRGB8888/ARGB8888) is converted to RGBA with a stride-aware row copy, honoring the `y_invert` flag.
* **Capture-before-content:** The fullscreen layer-shell overlay (`Layer::Overlay`) is committed at startup but presents **no image data until the first captured frame is ready**; the initial screencopy therefore never contains the overlay, avoiding the Droste-effect self-feedback that plagues live-capture magnifiers.
* **Frozen view:** After the first frame, the overlay displays a nearest-neighbor zoomed view of the frozen frame. Zoom keys `1`–`9` re-scale the same frozen frame; the screen is never re-captured at runtime.
* **Fullscreen viewport at launch:** The viewport covers the **entire physical screen** from the very first presented buffer — including any shell bars (e.g., the Noctalia shell top bar) in the magnified capture — with **no compositor window rules** required. The layer-shell overlay is created on the **Overlay layer** (topmost) with **all anchors** and an **exclusive zone of −1** ("dont care"): without it, niri/Smithay shrinks the overlay geometry around the reserved zones of bars/docks (e.g., the Noctalia top bar) regardless of layer, leaving the real bar covering the magnifier's top strip. The surface explicitly requests the **full output logical size** and **re-asserts it on every configure**, **redrawing immediately** whenever a configure changes the size. The **GPU (EGL) window is initialized lazily at the first configure**, when the real output logical size is known, so the very first presented buffer is already fullscreen: creating the `wl_egl_window` with a hardcoded size and calling `wl_egl_window_resize` before the first `eglSwapBuffers` has no effect on the first attached buffer, which previously left the viewport smaller than the screen until the first pointer motion triggered a second swap (regression fixed in commit `99d2dd2`).
* **Failure handling:** A failed capture is retried up to **3 times**; if all retries fail, the overlay renders black.
* **Secure windows capture black (expected):** some apps appear **solid black** in the frozen frame — e.g. KeePassXC over niri — because the compositor's own security feature (**niri's `block-out-from "screen-capture"` window rule**) replaces matching windows with solid black in automated capture buffers (wlr-screencopy and portal screencasts). This is compositor-side and intentional; a client cannot and must not bypass it. It is not a bug in the capture path.
* **Zoom centering:** The viewport follows the **live cursor** over the frozen frame — the view is centered on the content under the cursor; if the cursor was never seen, it centers on the capture. The **magnified cursor is always drawn at the dead center of the viewport** (in every mode, including while panning, zooming, easing or hold-zooming): only the magnified screen moves when the mouse moves. Zoom keys `1`–`9` re-scale.
* **Cursor-following motion:** The view is panned **relative to the hand's movement** (per-event deltas in logical pixels mapped into source space via per-axis source/viewport ratios `scale_x`/`scale_y`, so capture buffers whose aspect ratio differs from the output are handled correctly). The view center is never re-derived from the hand's *absolute* position after launch, so the view can never jump to the hand: **releasing hold-to-zoom (or any other state change) leaves the view exactly where it is**, and the next mouse motion pans it smoothly. The view center is initialized **once, on the first pointer enter, to the launch cursor's content** (a draw before the enter would otherwise leave it at the capture center), preserving the "start exactly where the cursor was" behavior; later pointer enters never re-center. Positions are tracked at sub-pixel precision, shifting the magnified content continuously on the CPU fallback (bilinear) and quantized to source texels on the GPU path (nearest-neighbor).
* **Input responsiveness during animation:** Keyboard input (the app's own global keys — zoom/OSD/screenshot bindings) works even while the panning animation is running: the **EGL swap interval is set to 0** so frame redraws never block the event loop. The layer surface's keyboard interactivity is **`on-demand`** (not `exclusive`), so compositor-level global keybindings keep working.
* **Motion redraw rate cap:** pointer events arrive at the libinput sample rate (up to ~1000 Hz for high-polling mice), and redrawing + presenting a full-screen frame for each one floods the compositor with commits — the observed panning lag when launching over a continuously repainting surface (e.g. a web browser with hover effects/animations/video) versus the snappiness over an idle one (e.g. Blender's viewport). Motion-driven redraws are therefore **capped at one per 8.33 ms (≈120 Hz)** (`MOTION_REDRAW_INTERVAL`): the **first event of a burst draws immediately** (lowest latency) and any motion within the interval is **coalesced** into a single scheduled draw fired by the event loop's bounded poll on the deadline (the same `dispatch_with_timeout` machinery as nudge-repeat — compositor-independent, no reliance on frame callbacks). State updates (pan, hold-to-zoom, reach tracking) stay **per-event** (cheap); only the full-frame draw + present is throttled, so panning stays just as smooth (the display presents at 60–144 Hz anyway) while cutting compositor load by an order of magnitude. All other redraw triggers (scroll, keys, screenshot mode, Configuration window) are unchanged and draw immediately.
* **Compositor occlusion independence:** The layer surface is marked **fully opaque** via `wl_surface.set_opaque_region` (covering the whole output — the magnified frame, the black bars beyond it, and every cursor/OSD/selection blend produce opaque pixels everywhere, so the surface genuinely is opaque). Compositors use opaque regions for occlusion culling, so anything fully covered by the magnifier stops being composited: a constantly repainting app underneath (e.g. a browser with hover animations, video, or a blinking caret) no longer contributes compositor load while Maggie is up, making smoothness independent of whatever app was visible at launch. **GPU routing is decided by the compositor, not the client:** `eglGetPlatformDisplay(EGL_PLATFORM_WAYLAND)` hands clients the compositor's *client-buffer* device, and **EGL-on-Wayland offers no client-side GPU selection** (verified: `DRI_PRIME=1` makes Mesa fall back to `llvmpipe` software rendering; forcing the NVIDIA EGL vendor breaks init entirely). The startup log line `EGL GPU: <vendor> — <renderer>` (from `glGetString(GL_VENDOR/GL_RENDERER)` after `gles2::load_with`) makes the routing verifiable at a glance. On the reference setup (CachyOS, niri, Intel UHD + RTX 4070, panel on the Intel eDP connector) the whole stack — niri, Maggie, and the browser — renders on the **iGPU** (`EGL GPU: Intel — Mesa Intel(R) Graphics (RPL-S)`), with the RTX 4070 essentially idle, which is why a constantly repainting browser is expected to contend with Maggie on the shared iGPU. The lever is **compositor-level**: niri's `debug { render-drm-device "…" }` option (or the UEFI MUX switch to discrete-GPU mode) makes the compositor render on the dGPU, which moves all EGL clients there too — at the cost of battery life.
* **Viewport rendering:** The viewport is rendered from the frozen frame as a textured quad. The **GPU path** samples the frame texture into a buffer at **2× the layer's logical size** (`wl_surface.set_buffer_scale(2)`): the **min filter is `GL_LINEAR`** so zooming out below 1× (e.g. the fully-zoomed-out view) downscales smoothly instead of aliasing — plain nearest-neighbor minification made text look degraded at small zooms — while the **mag filter stays nearest-neighbor**, preserving the crisp, pixelated magnifier look when zooming in. The **CPU fallback** (`src/render.rs`) renders with **bilinear interpolation** at fractional source offsets, shifting the magnified content continuously. Both paths paint the region beyond the capture **solid black** (the view *region* is not clamped — the view center is, so near the screen edges the region samples past the frozen frame while the cursor stays inside the capture). **Pixel-grid lock (“snap at launch and that's it”):** the magnified cursor sits **exactly at the dead center** at all times — it never moves on its own (no self-animation, no snap, no jitter) — so the magnified screen moves while the magnified cursor stays still. For the cursor's texels to coincide with the screen's texels, the capture pixel under the cursor must be an exact integer — which is only possible if the content slides in **whole-texel steps** (one capture px = one magnified block). The view center is therefore **quantized to the nearest integer capture pixel and permanently kept on that lattice** (`quantize_center_to_pixel_grid`, applied in `draw_frame` after clamping and edge-reach, written back to `view_center`): the *launch snap* the user asked for, applied once and then held for every subsequent pan and zoom. Result: the capture texel under the cursor starts exactly at the viewport center, so the cursor's blocks and the screen's blocks share one lattice — pixel-perfect flush alignment at every zoom, permanently, with the cursor pinned and nothing ever adjusting itself afterwards. The OSD readout and minimap marker use the quantized (integer) center, so they show the true physical pixel under the cursor. At fractional zooms (hold-to-zoom levels like 1.33×) the two lattices still coincide exactly (both are `viewport_center + m × px_per_texel`), though individual blocks are inherently 2-or-3-px wide there. The trade-off is that panning moves in whole-texel steps (e.g. 3 logical px at 3×, 8 at 8×) — sub-texel panning is geometrically incompatible with a pinned, permanently aligned cursor. Vestigial: `snap_render_origin` and a screen-settle (a sub-block image shift at rest) remain in the source tree only as tests/experiments — neither is active, and the settle was rejected by the user as a visible secondary motion.
* **Scroll-wheel zoom:** The scroll wheel zooms in/out in one of two modes selected by `scroll_zoom_mode` (§4): **`levels`** (**default** — each notch steps between the discrete levels of the `1`–`9` keys — level *i* = `max_zoom` × *i*/9 — **extended with a level 0 at the runtime minimum** (1×, or the fully-zoomed-out view — the whole captured screen filling the viewport — when `allow_zero_zoom` is on), so the **most zoomed-out level is always reachable with the wheel** even when `max_zoom`/9 > 1× (e.g. max 12 used to bottom out at 1.33×, unreachable with a 1× default); on a level it steps to the neighbour, off a level it snaps to the next level in the scroll direction) or **`factor`** (each notch multiplies the zoom by **10 %**, clamped to the runtime minimum..`max_zoom`). By default the wheel direction is reversed compared to conventional zoom (wheel-up zooms **out**, wheel-down zooms **in**); the `invert_scroll_zoom` option (§4) flips back to the conventional direction (wheel-up zooms in). High-resolution `value120` wheel deltas are supported; continuous touchpad scroll is ignored.
* **Hold-to-Zoom:** While the **`hold_to_zoom`** modifier (default **`Super`**) is held, **vertical pointer motion zooms continuously** — moving up zooms in, down zooms out, at a rate of `hold_to_zoom_speed` zoom-units per pixel (default `0.02`, so the full 1×–9× range takes 400 px of travel) — clamped to the runtime minimum (1×, or the fully-zoomed-out view when `allow_zero_zoom` is on)..`max_zoom`. **Floor hold:** while the zoom sits exactly on the runtime minimum (the `0x` fully-zoomed-out view), zoom-out holds the floor rock-solid and zoom-in is ignored until ~2 px of committed upward motion (a small dead zone) — tiny alternating pointer jitter at the floor used to flap the zoom between the floor and one step above it (`0.57x ↔ 0.59x`). The zoom change is **position-based per motion event**, so it stays buttery-smooth at any event rate (no stepping, unlike the wheel's level/factor modes). **Horizontal motion is unaffected**: it still pans the view normally. The modifier press arms the feature with the current pointer Y as baseline (no initial jump); releasing it disarms; while the Configuration window is open it is forwarded to egui and does nothing. **No drift, no jumps:** while held, vertical motion **only** zooms and horizontal motion **only** pans — so the view y stays locked to the content under the centered cursor and the **magnified cursor never leaves the dead center of the viewport**: the same guarantee a wheel zoom gives, at any zoom. On **release** nothing is repositioned and nothing re-centers: the view stays exactly where it is and the next mouse motion pans it by its relative delta — **no jump at release and no jump on the first motion after release**. **Offset correction:** because the view y was locked while the hand travelled to zoom, release leaves the view offset from the hand's content; left alone, that offset shifts the reachable pan range and creates invisible limits. The residual offset is therefore **derived continuously** (view minus hand content, recomputed on every motion event) and **corrected by subsequent real pointer motion** — moving *away* from the hand content (or gliding) pans the view 1:1 with the hand and leaves the residual untouched, so a large residual can never stick the view or reverse its direction; moving *toward* the hand content erases the residual via the catch-up below — restoring the full pan range **without any jump or self-animation** (nothing moves unless the hand moves). **Reach-restoring boost:** a residual always blocks the wall in the direction it points away from — pushing there used to stop short by the residual (an "arbitrary distance" that grew with fast motion, because a quick push to the wall gave the slow decay no time to finish). So whenever the pointer moves **toward the hand content** (the reach-blocking direction), the correction is boosted to at least the hand's own per-event travel (capped at 2× the hand's speed, never overshooting the hand): the residual is erased **during the push itself**, so the far wall is reached **exactly, at any speed, immediately after hold-to-zoom** — with no jump and no self-animation (the view never moves unless the hand does, and never faster than 2× it). Moving away from the hand content does **not** heal at all: the view pans 1:1 with the hand, so a deep hold-to-zoom drag's large residual can never stick the view (a bounded heal used to leave it momentarily stuck) nor drive it against the drag direction (it used to flip the pan: mouse-down moved the view up, the same direction as mouse-up). The residual is erased only when the pointer moves toward the hand content, and both walls stay reachable regardless — the plain pan clamps the view to the capture at the far edge, and the hand-edge reach snaps it there exactly. **The correction never fights a wall:** the view is hard-clamped to the capture *before* correction, and any axis already pinned against a capture edge is left untouched by the correction — so pushing against a screen edge always lands the view **exactly** on the edge, and gliding along an edge keeps the view on it, regardless of pointer speed or the size of the residual offset. **Hand-edge reach:** the view pans with the hand's *movement*, so its reach is bounded by the hand's delivered travel — and the compositor's **last delivered pointer position can lag the hand's true stop when the pointer is moved fast**: the gap is the travel the hand covered after the last delivered sample, which was accumulated at the **peak speed of the flick, frames before the hand decelerated**. That is exactly why walls used to stop short at speed (the current event's own, already-decelerating travel under-covers the gap) while slow motion always reached. So when the pointer is **pushing toward a wall, the reach margin scales with the pointer's recent peak travel** (a rolling max over the last 4 motion events, `peak × 1.5 + 8` logical px, capped at 200): the margin never drops below the coverage of the pointer's current speed (the current event is always in the window, and the delivery gap is at most the final frame's travel) and additionally covers a delivery staleness of a few frames while the fast phase is recent — and is small while the pointer is moving slowly (no magnetic wall — parking stays precise anywhere), so the view is placed **exactly on the capture edge at any speed**. The window is flushed after a pause and on hold-to-zoom release so an old fast phase can never make a later slow crawl magnetic. The view must already be within the (scaled + 8 px slack) margin of the wall, so any jump stays the size of the delivery gap, never a large hold-to-zoom residual that is still healing. Pushing away, gliding, and mid-screen motion never trigger it, and **the reach is evaluated on every rendered frame** (`draw_frame` is the single choke point after any state change) using the **stored direction of the last motion event**, so it fires even when the pointer stops short of the physical edge and no further motion events are delivered (a per-event evaluation could otherwise miss the final shortfall); while hold-to-zoom is active it applies to the x axis only, so the y-lock (the view y stays glued to the anchor content under the cursor) is never overridden; it never fires before the first motion event, so the launch centering on a near-edge pointer position is preserved. **Diagnostics** (`RUST_LOG=maggie=debug maggie`, now honoured by the log filter): near the surface edges every draw logs the pointer, surface, view before/after the reach, hand content, last-motion delta, recent peak travel and the computed reach margins, plus a greppable `SETTLED SHORTFALL` marker when the view is short of a wall while pushing into the edge zone — so the margin can be tuned against real delivered-position gaps instead of theory. In steady state the offset is exactly zero (the view pans 1:1 with the hand), so the correction is dormant during normal panning — but it is always armed, so **any** residual offset (hold-to-zoom, a launch race, a resize) is erased by toward-motion — a pinned axis holds the exact edge while the user is on it, and the residual vanishes once the hand catches up to the edge, at which point hand and view pin to the same value and the offset is zero. **Wall hold:** while the pointer rests at a physical edge (within the reach margin) and the view is within a small band of the wall (3 capture px), the view is held **exactly on the wall** even if sub-pixel pointer jitter would pull it off by up to that much — the delivered position near an edge oscillates (the hand can never hold the mouse perfectly still), and scaled up by the capture scale it used to cross rounding boundaries, making the OSD position readout and the magnified content shiver between wall and wall−1 at rest (worst at the right/bottom walls, where the resting delivered position sits below the edge). In steady state the view tracks the hand content, so the hold only fires while the pointer is within ~EPS/scale px of the edge; a deliberate pan away releases it immediately (no magnetic wall beyond the already-snapped edge). **Edge space:** because the cursor sits at the viewport center, the view may need to **sample past the frozen capture** near the screen edges — that region is always painted **solid black**.
* **Viewport edges:** The **view center never leaves the capture bounds** — it is hard-clamped to `0..capture_w × 0..capture_h` on every write (motion, hold-to-zoom, launch centering, and again in the render path as a final invariant). Because the magnified cursor sits at the viewport center (= the view center), this guarantees the cursor **never enters the black beyond-capture fill** and that **every captured pixel stays reachable** — pushing against a screen edge always lands the view exactly on the capture edge, so repeated left-right/top-bottom travel can never accumulate a reachable-range shift (no invisible limits). The magnified *view region* itself is not clamped: near the screen edges it still samples past the frozen frame, showing **solid black** beyond the capture; the cursor simply never sits in that black zone.
* **Magnified cursor (Implemented):** While the pointer is over the viewport, the **hardware cursor is hidden** (a blank 1×1 transparent ARGB cursor surface is set on `wl_pointer` enter, restored on leave) and the **real system cursor bitmap is drawn magnified**. To make sure the OS cursor can never appear anywhere — including the screen corners/edges, where shell surfaces (e.g. Noctalia hot corners) or a momentary leave of the layer surface used to show the compositor cursor — the pointer is additionally **confined to the layer surface** via `zwp_pointer_constraints_v1` (persistent lifetime, whole-surface region) whenever the compositor provides the protocol; the delivered position at the screen edges is then clamped exactly instead of oscillating sub-pixel-wise. Compositors without the protocol behave exactly as before. The frozen frame can never contain a baked copy of the system cursor because the screencopy is requested with **`overlay_cursor = 0`** — the wlr-screencopy protocol requires the compositor to exclude the cursor from the capture (honored by niri, wlroots, KWin, Hyprland, …), independent of pointer focus or timing. The **first capture is requested at the first configure, before anything has been rendered** — the frame appears immediately after launch, contains no feedback copy of the magnifier's own overlay (nothing has rendered yet), and the view centers exactly on the pointer's launch position when the pointer enters the surface. *inside* the view at the exact spot where the content under the pointer lands. On startup the cursor theme is loaded from disk (`$XCURSOR_THEME`, default `default`/`Adwaita`, via the standard icon search paths) and parsed with the `xcursor` crate; the pointer's **hotspot** is honored, so the arrow tip lands exactly on the content under the cursor. The image is **nearest-neighbor upscaled by the zoom level** (and the 2× render buffer on the GPU path), so it magnifies along with the visuals. It **tracks the live pointer on every motion event** (never a static sprite). If no theme is found, it falls back to a stylized reticle (white ring, black center). Rendered on both the GPU path (alpha-blended textured quad via the sprite shader, pre-scaled to the 2× render buffer) and the CPU fallback (alpha-blended blit, `MagnifierWindow::draw_cursor_at`). See §5.
* **No live mode:** Continuous live capture is explicitly **out of scope**; the interactive live-magnifier idea (including an earlier planned `--live` flag) was dropped. Behavior modes that assumed a live view (see §6) are obsolete until redefined.

## 4. Configuration System — *Partial*
* **Location:** XDG standard configuration directory (`~/.config/maggie/`).
* **Format:** `.ron` (Rusty Object Notation) configuration file.
* **Storage Requirements:**
  * **Default Zoom Level** (floating point, default `2.0`, clamped to the runtime minimum..`max_zoom`; a default of exactly **0 % auto-enables `allow_zero_zoom`** and locks it while it stays at 0 — the app then launches fully zoomed out, the whole screen visible).
  * **Max Zoom Level** (`max_zoom`, floating point, default `9.0`, range 1×–32×): the ceiling for the zoom keys, the scroll wheel, hold-to-zoom, and the default zoom.
  * **Hold-to-Zoom Speed** (`hold_to_zoom_speed`, floating point, default `0.02` = 2 % zoom per pixel of vertical motion, range 0.001–1.0): rate of the smooth hold-to-zoom feature — see §3.
  * **Allow 0% Zoom** (`allow_zero_zoom`, boolean, default `false`): when enabled, the scroll wheel, hold-to-zoom and the `1`–`9` preset keys may zoom out below 1×, down to the **fully-zoomed-out view** ("0 %" — the whole captured screen filling the viewport; never a literal 0×/black screen, which used to make zooming out look broken). When disabled the minimum is 1×. **Forced on and locked** while `default_zoom` is exactly 0 (the Configuration window shows a warning that disappears once the default is above 0). The **`0` key always selects the fully-zoomed-out view** regardless of this setting. The OSD zoom readout displays **`0x`** whenever the zoom is at the fully-zoomed-out view (and otherwise the plain factor, e.g. `3.00x`), so reaching the minimum reads unambiguously as 0; a `%` readout was tried first but the built-in bitmap font's `%` glyph was illegible (read like a `2`).
  * **Scroll-Wheel Zoom Mode** (`scroll_zoom_mode`): `levels` (default) | `factor` — see §3.
  * **Invert Scroll-Wheel Zoom** (`invert_scroll_zoom`): boolean, default `false` — see §3.
  * **OSD Visibility** (`show_osd`): boolean, default `true` — see §7.
  * **Keybindings** for all in-app functions. Defaults: `toggle_osd` `K`, config window **`Tab`** (was `C`), `toggle_cursor` **`C`**, `minimap` **`M`**, `hold_to_zoom` **`Super`**, `reset_zoom` `R`, screenshots `F`/`G`/`W` (manual Screenshot Mode moved from `S` to `G` so the WASD keys are owned by border nudging), anti-aliasing `A`.
  * **Screenshot Path** (default: `~/Pictures`).
  * **Screenshot Filename Pattern:** Utilizes standard `strftime` formatting tokens (supporting dynamic variables such as `%Y` for year, `%m` for month, `%d` for day, `%H` for hour, `%M` for minute, etc., defaulting to `maggie_%Y%m%d_%H%M%S.png`).
  * **Screenshot Selection Color** (`screenshot_selection_color`, RGB tuple, default `(255, 153, 0)` orange): the border color of the selection rectangle in Screenshot Mode (picked with an egui color button in the Configuration window).
  * **OSD Legend Corner** (`osd_corner`, enum, default `top-left`): the corner where the OSD key legend is placed. With the centered cursor scheme the legend no longer relocates dynamically — it stays in the configured corner. Values: `top-left`, `top-right`, `bottom-left`, `bottom-right`.
  * **Minimap Corner** (`minimap_corner`, enum, default `bottom-right`): the corner where the minimap overview is placed. If it coincides with `osd_corner`, the minimap is automatically pushed to the diagonally opposite corner to avoid overlap.
  * **Minimap Visible at Launch** (`minimap_visible`, bool, default `true`): whether the minimap overlay is shown when Maggie starts (the `minimap` key still toggles it at runtime).
* **Serde defaults:** Newer options (`scroll_zoom_mode`, `invert_scroll_zoom`, `show_osd`, `max_zoom`, `allow_zero_zoom`, `keybindings.reset_zoom`, `keybindings.toggle_cursor`, `keybindings.hold_to_zoom`, `keybindings.screenshot_manual`, `keybindings.minimap`, `osd_corner`, `minimap_corner`, `minimap_visible`) carry `#[serde(default)]`/`#[serde(default = …)]`, so config files written before these options existed remain loadable (unknown/removed fields like `cursor_follow`, `htz_edge_behavior`/`htz_edge_fill` are ignored by ron); `max_zoom` and `default_zoom` are normalized on load (NaN/out-of-range values dropped, default clamped to the max).
* **Status:** Loading from disk is implemented; the listed `strftime` tokens are evaluated on save. Persistence is wired through the Configuration window (§9) — changes are auto-saved on change (snapshot drift detection); the explicit **Save** button also writes.

## 5. Visuals & Rendering — *Implemented* (AA toggle: *Stub*)
* **Zoom & Scaling:** Controlled via numeric keyboard keys `0` through `9` — the **`0` key selects the fully-zoomed-out view** (the whole captured screen filling the viewport; always available, shown permanently in the Key Legend), and keys `1`–`9` each select a **percentage of the configured max zoom** (key *i* = `max_zoom` × *i*/9, so key 9 is always the maximum; with the default `max_zoom = 9` the keys map to 1×..9× exactly as historically; with `allow_zero_zoom` enabled the keys may go below 1×, down to the minimum) — or the scroll wheel (`levels` mode: steps between those same levels plus the minimum; `factor` mode: 10 % steps up to `max_zoom` — see §3). The **middle mouse button** (and the `reset_zoom` keybinding, default `R`) resets the zoom to the **default zoom**; keys and wheel re-scale the frozen frame.
* **Rendering Preference:** The default **GPU path** (EGL/GLES2) renders the viewport at a **2× buffer scale**: **nearest-neighbor magnification** for the crisp, pixelated magnifier look when zooming in, and a **`GL_LINEAR` min filter** so zooming out below 1× downscales the frozen frame smoothly (nearest-neighbor minification used to alias text at small zooms); sub-pixel cursor-following is then quantized to source texels (see §3). The **CPU fallback** uses **bilinear interpolation**, which shifts the magnified content continuously during sub-pixel cursor movement. The active path is selected automatically at startup — GPU if EGL/GLES2 initializes, CPU otherwise (see §2).
* **Anti-Aliasing Toggle:** An optional toggle bound to the `A` key, implemented only if it does not introduce development complexity. — *Stub: key is bound but not yet functional.*
* **Magnified cursor rendering:** `src/cursor.rs` (`MagnifiedCursor`) loads the **system cursor theme bitmap** at startup (`xcursor` crate parses the `.cursor` file; premultiplied ARGB pixel data is converted to straight alpha) and caches it as the base image. Each frame it is **nearest-neighbor upscaled** by `zoom × render_scale` into an RGBA buffer; the image's **hotspot** (scaled identically) is passed to the renderer so the cursor tip tracks the content under the pointer. Its visibility inside the viewport is toggled with the **`toggle_cursor`** key (default `C`, separate from the hardware-cursor hiding). **Why load the theme file instead of the live cursor:** Wayland exposes no protocol to read the compositor-drawn hardware cursor bitmap, so the app reads the same theme files the compositor uses from disk. The sprite is composited above the magnified frame and below the OSD legend. On the GPU path it is drawn with a dedicated sprite vertex shader (rect placement in `u_rect`, explicit NDC y-flip, full-texture sampling) at `RENDER_SCALE` resolution so it matches the crisp 2× buffer; on the CPU path it is blitted at logical scale (`MagnifierWindow::draw_cursor_at`). The OSD legend is placed in the **configured corner** (`osd_corner`, default `top-left`, configurable in Configuration) — no longer relocating dynamically since the centered cursor scheme makes the farthest-corner heuristic unnecessary.
* **Minimap (toggle key `M`, `keybindings.minimap`):** An overview panel **visible by default at launch** (`minimap_visible`, default `true`, configurable in Configuration as "Show minimap at start"), placed in the **configured corner** (`minimap_corner`, default `bottom-right`; if it shares a corner with the OSD it is automatically pushed to the opposite corner). Shows a **toned-down** (box-average downscaled, dimmed to ~45 % brightness) thumbnail of the **whole captured screen only** (the area the user can travel in — never includes the black space beyond the capture edges). The thumbnail keeps the capture's aspect ratio and is ~22 % of the viewport width (clamped to 140–360 px), framed by **three concentric square borders with sharp corners** (outer white → middle black → inner white, **each 2 px wide**) with a translucent dark interior. Two markers are drawn on top: **amber corner brackets marking the visible magnified region** (camera-viewfinder style: short 7 px L-shaped ticks at the four corners of the view source rect, clamped to the capture — at the fully-zoomed-out view the brackets hug the thumbnail's corners; **skipped when the mapped region is smaller than ~12 px**, i.e. roughly the marker size, so it can never degrade into a stray corner pixel behind the dot at deep zoom) and a **red filled circle with a 1 px black outline at the exact cursor position** (the viewport center, where the magnified cursor sprite always sits; drawn per scanline as a true circle, no degenerate edge pixels). The base (borders + dimmed downscale) is **cached per capture/size** and only the small marker overlay is redrawn each frame, so the per-frame cost is a tiny buffer copy + texture upload even while panning at full speed. **Baked-cursor scrub:** the launching app's *own* cursor graphic (XWayland / software cursors, which `overlay_cursor = 0` cannot exclude) can be baked into the frozen frame at the launch pointer position; the minimap base scrubs that region (ring-average fill around the recorded launch position, [`CURSOR_BAKE_HALF`] = 24 capture px) before downscaling so no stray miniature cursor appears next to the marker — the scrub affects **only the minimap base**, never the magnified view or screenshots. On the GPU path the sprite is drawn last (on top of the frame, overlay and OSD) as a dedicated `minimap_tex` sprite whose texture stays at logical resolution and is LINEAR-upscaled to the RENDER_SCALE surface; on the CPU fallback it is alpha-blended into the canvas at its corner position. The minimap is **toggleable in Screenshot Mode as well** (the key works there, and the line appears in both legends); the toggle is purely visual — it never affects panning, zooming or the captured frame.

## 6. Behavior Modes — *Revised*
* The former **Center Cursor** / **Edge Pan** / **Miniature Window** modes remain **obsolete/removed** in the frozen-frame model; they are pending redefinition or removal. Mode-switch bindings (`Ctrl+C`/`Ctrl+E`/`Ctrl+M`) still exist in code but have no rendering effect.
* **Cursor-following:** The former "Center Cursor" concept is now the **built-in default behavior** of the frozen viewport — the view follows the live cursor over the frozen frame with the magnified cursor always pinned at the viewport center; near the capture edges the view extends past the frame (black fill). See §3.

## 7. OSD (On-Screen Display) Key Legend — *Implemented*
* Toggable via the `K` key (configurable via `keybindings.toggle_osd`).
* **On by default**, configurable via the `show_osd` configuration file option (§4).
* Dynamically stays or moves out of the way of the cursor position: the legend box is placed in the **corner farthest from the cursor** (4-corner logic, considering the box center).
* The legend background is **opaque** (solid dark box, alpha 255) so no magnified content or text ghost shows through.
* Rendered with a built-in 5×7 bitmap font (`src/osd.rs`) drawn at **4× scale** (5×7 glyphs scaled 4×, i.e. rendered at 20×28) with doubled box padding/margin — the legend was enlarged 2× for readability; the header reads **`maggie vX.X.X`** (version pulled from `Cargo.toml` at compile time via `env!("CARGO_PKG_VERSION")`); lists zoom level, a **`pos WxH` cursor-position line** (the view center in capture px — the frozen frame is the output at native resolution, so capture px are the **real physical screen pixels** under the centered cursor; shown only once the first capture settles the view center, never a placeholder), `0`–`9` zoom, `K` OSD toggle, `F` fullscreen screenshot, `G` manual screenshot, `W` window (stub), `Tab` config window, **`C` toggle cursor**, **`M` toggle minimap**, **`hold Super` + move smooth zoom**, **`MMB`/`R` reset zoom**, and `Q`/`Esc`/`RMB` quit.
* **Rendering fix:** The OSD quad is drawn with its own dedicated vertex shader that samples textures **top-down**, because the captured frame texture is stored **bottom-up** (screencopy `y_invert`) so the main shader's Y-flip compensates it. Previously the top-down OSD sprite was rendered upside down and outside its box, leaving only the opaque background visible as an empty black box; the legend text now renders upright inside the box.

## 8. Screenshot Subsystem — *Partial*
Triggered using dedicated keybindings (`S`, `W`, `F`); a unified **Screenshot Mode** with a live selection overlay (opaque orange border ring on the undimmed magnified screen, **`screenshot_selection_color`**, default orange, configurable in the Configuration window):
* **Manual Selection (`G`; was `S` — existing configs migrate):** Enters Screenshot Mode with no selection; **LMB drag** draws the rectangle over the frozen frame (in capture px, so the view never pans while selecting). **The selection is pixel-snapped:** the drag anchor (on press) and the live corner (while dragging) are snapped to the **nearest whole capture pixel** — the grid the user sees as the magnified pixels (each magnified block is one capture px scaled by the zoom; the GPU path renders with `GL_NEAREST` magnification, so the grid is crisp) — so the rectangle always aligns with the magnified pixel grid in capture space instead of floating at arbitrary sub-pixel positions. Because the rect is integer-valued in capture px, the saved crop is **exactly** the visually selected region: the save path rounds independently, and an un-snapped fractional rect could otherwise crop up to a pixel off from what was shown on screen. (The on-screen border is drawn at the nearest screen pixel; with a fractional frozen-view offset it can sit up to half a logical pixel off the true block boundary — quantizing the view to remove even that would visibly jump the image on mode entry, which the user explicitly rejected.) Nudges (`WASD`, ±1 px) and the fullscreen selection keep the same integer alignment. In Screenshot Mode the **magnified cursor follows the live pointer** (only the view stays put), so the user can aim it at a border before nudging — and **entering the mode never jumps the cursor**: the sprite is anchored to its current visual position (the viewport center) with a captured pointer offset, so pressing `G` keeps the cursor exactly where it was and only *relative* pointer movement moves it. The **drag draws with the visible cursor**: the selection rectangle is anchored to and tracks the sprite position (pointer + entry offset), never the raw physical pointer, so the rectangle and the cursor the user sees can never diverge. **The selection overlay is cached** (keyed on mode + selection rect + active border): plain pointer motion neither refills nor re-uploads the full-screen overlay buffer (45 MB at the 2× render scale), so the mouse stays as smooth and snappy in Screenshot Mode as in the magnifier — the overlay rebuilds only when the mode, the selection, or the highlighted border actually changes. **The overlay is drawn as a bounded ring with no dimming** — the scrim is fully transparent, so the magnified screen stays **opaque and undimmed** everywhere, exactly as it looked in the magnifier just before entering the mode (the transparent full-buffer reset also clears any stale pixels from an earlier selection, since the buffer is reused across rebuilds): only the opaque border ring (bands limited to the rect's own edges, active edge thicker/lightened and drawn last so it wins the corners) marks the selection. A 1-px click rect renders as a small outlined box — never full-width horizontal or full-height vertical lines spanning the screen — and a rect narrower than its own border widths degrades to a no-op instead of an inverted-range slice panic, so fast diagonal drags can never crash the render. — *Implemented.*
* **Fullscreen Selection (`F`):** Enters Screenshot Mode (or, inside it, re-selects) with the **whole frozen frame selected**; Return saves. (Previously `F` saved immediately; the selection flow now requires Return.) — *Implemented.*
* **Confirming (`Return` / keypad Enter):** Crops the frozen frame to the selection and saves it as a PNG via **Output Path Generation**; a transient *"Saved <path>"* heads-up shows in the OSD legend for ~4 s (the legend is **forced on** for this even when the OSD is toggled off). — *Implemented.*
* **Cancellation:** **Escape**, `Q` or **RMB** during Screenshot Mode cancels without quitting (outside the mode these retain their normal meanings). Opening the Configuration window (`Tab`) also cancels the selection first. The **Key Legend stays toggleable in Screenshot Mode**: the **toggle-OSD key (`K`)** still hides/shows the Screenshot-Mode legend. — *Implemented.*
* **Nudging (WASD):** With a selection marked, the **border closest to the magnified cursor** (in Screenshot Mode the cursor sprite follows the pointer — that position is the 'click anchor') is nudged **1 real pixel per keypress** (1 capture px = 1 physical screen pixel; the *saved image* changes by exactly 1 px per nudge — at high zoom this naturally renders as `zoom` viewport px, which is correct for a precise crop). **The active border needs no proximity:** the closest edge to the cursor is always the one WASD affects, wherever the cursor is (ties broken deterministically left < right < top < bottom), and it is **highlighted** (thickened and lightened toward white) in the overlay so the user can see which edge will move. **Closeness is measured to the visible border segments, not infinite lines:** the distance to each edge is the distance to its finite drawn segment (between the two corners), so on a wide rectangle a cursor far to the right selects the short right edge — never the long top/bottom edges, whose infinite-line distance would otherwise win. **Every border moves in all four directions**: the on-axis keys move that edge itself (top/bottom with `W`/`S`, left/right with `A`/`D`), and the off-axis keys **translate the whole rectangle** along that axis (e.g. `A`/`D` while a top/bottom edge is active shifts the entire selection horizontally, `W`/`S` while a left/right edge is active shifts it vertically), preserving its size — a translate that would push any part of the rectangle out of the capture is simply ignored (never shrinks). The rectangle never collapses below 1 px or leaves the capture. **Held WASD keys repeat** — an **app-side repeat** (400 ms delay, then ~30 Hz) driven by the **event loop itself**: pressing a nudge key arms a deadline; the loop's bounded poll (`dispatch_with_timeout`, mirroring `blocking_dispatch` with a timeout = time until the next deadline) wakes on the deadline even with zero events and `draw_frame` fires one nudge per interval on a drift-free cadence; releasing the key (or leaving the mode) stops it. This is compositor-independent and deterministic: niri does not deliver `wl_keyboard` repeated-key events to a client running a manual event loop, sctk 0.21's built-in client-side repeat requires a calloop `LoopHandle` this app does not run, and a frame-callback-driven clock proved unreliable on niri (repeats only fired while mouse motion happened to wake the loop) — so the compositor's repeated-key path is kept only as a guarded fallback and can never double-fire with the timer. (The spec's earlier "Arrow keys" wording is superseded by WASD.) — *Implemented.*
* **Default screenshot scale (`screenshot_scale`, default `real`):** Saved screenshots are either the **real pixels** of the selected region (`real`, 1 saved px = 1 captured px) or the region **magnified to the current zoom** (`magnified`, nearest-neighbor upscale matching the crisp magnifier look; clamped to real size when zoomed below 1×). Chosen with a dropdown in the Configuration window. While in Screenshot Mode the **`screenshot_scale_toggle` key (default `V`)** flips the *effective* scale between real and magnified on the fly (each mode entry starts at the configured default; the current one is shown in the Screenshot-Mode Key Legend) and the next save honors it. — *Implemented.*
* **Window Selection (`W`):** Displays a dynamically sized grid representing all available windows for capture. Clicking an item captures and saves that specific window. — *Stub: not yet implemented.*
* **Output Path Generation:** Combines the configured `screenshot_path` with the evaluated `strftime` filename pattern (`~` expansion and directory creation included). `~/X` is expanded as `home/X` — the remainder after `~` is **stripped of its leading `/`** before joining, because `Path::join` treats a leading `/` as an absolute path and would otherwise place screenshots at `/X` (filesystem root), where `create_dir_all` fails with permission denied (os error 13). — *Implemented.*

## 9. Configuration Window — *Implemented* (GPU path)
* Activated via the **`Tab`** key (`keybindings.config_window`; changed from `C` so `C` could become the magnified-cursor toggle); closed with the **Close** button or **Escape**.
* Built with **egui 0.35 + egui-glow** (`src/config_window.rs`) painted directly into the same EGL surface through a `glow` context sharing the app's GLES2 function pointers — no separate toplevel window is created (Maggie is a full-screen layer-shell overlay). Requires the **GPU render path**; on the CPU fallback the key logs a warning.
* While open, the whole surface shows the UI, **pointer and keyboard events are forwarded to egui** (motion, buttons, wheel, keys via an xkeysym→`egui::Key` mapping, text input, modifiers), and the magnifier's own key handling (zoom keys, Q/Esc quit) is suspended. Keyboard interactivity stays **`on-demand`** throughout (never toggled): niri grants it at map time and on every click, so text fields receive keys after the first click — and critically, *not* switching to `exclusive` means niri never clears its remembered on-demand focus, so closing the window leaves the magnifier's global keys working immediately (an `exclusive`→`on-demand` round trip would drop focus until the next click).
* **Fonts:** The window uses larger base fonts (body 19 pt, headings 28 pt, small/hint 16 pt) for readability on the full-screen surface.
* **Exit guidance:** The footer explains that the window is closed with the **Close** button or **Escape**, that the magnifier's keys resume afterwards, and that `Q`/`Esc`/`RMB` quit Maggie when the window is closed.
* **Cursor while open:** The hardware cursor is replaced by a **real cursor surface built from the loaded system cursor theme** (`config_cursor_surface`; the straight-alpha theme bitmap is premultiplied into an ARGB8888 shm buffer, hotspot honored via `set_cursor`), so the UI shows a normal, visible pointer. It is re-asserted on every pointer **enter** (fresh serial) and on every **button press** (fresh serial) to defeat stale-`set_cursor`-serial drops by the compositor; the blank surface is restored on close. The pointer confinement (§3) applies to the whole layer surface, and since the Configuration window renders into that same surface, the visible cursor works everywhere in it — the former hot-corner flicker is gone on compositors with pointer constraints.
* **Instant Application:** All settings are edited live (no separate Apply step) — `default_zoom`, `scroll_zoom_mode`, `invert_scroll_zoom`, `show_osd`, screenshot path/pattern, screenshot selection color, and all keybindings.
* **Persistence:** Changes are **auto-saved on change** — every frame the live config is compared against the last-persisted snapshot (`MagnifierConfig: PartialEq`); any drift (a modified field, a picked folder) is written to disk immediately, so settings survive restarts without clicking anything. The **Save** button still writes explicitly, **Reload** re-reads from disk and resets the snapshot, and a status line reports outcomes. `default_zoom` is normalized on load (NaN / out-of-range values dropped) so a hand-edited file cannot poison the drift check. The `default_zoom` field is edited through `get_or_insert` (a previous `unwrap_or` edited a temporary, so the setting silently never changed).
* **Folder picker:** A **Browse…** button next to the screenshot path opens a native folder-picker dialog (`egui-file-dialog` 0.14, `pick_directory`/`take_picked`) built **non-modal** (`as_modal(false)` — the modal overlay is a full-screen interactive backdrop that can sit above the dialog in a hand-painted egui setup and swallow all clicks) and — the actual click fix — **rendered inside the same egui pass as the rest of the UI**: `FileDialog::update(ctx)` is called inside the `run_ui` closure (previously it ran *after* the pass ended, so the window was drawn a frame late and its widgets' pointer clicks were hit-tested against stale input — only scroll and keyboard navigation reached it); the chosen directory is applied to `screenshot_path` and auto-saved.
* **Settings covered:** `default_zoom` (clamped to the runtime minimum..`max_zoom`), `max_zoom`, `hold_to_zoom_speed`, `allow_zero_zoom` (locked while default zoom is 0, with a warning; "0 %" = fully zoomed out), `scroll_zoom_mode`, `invert_scroll_zoom`, `show_osd`, `minimap_visible` ("Show minimap at start"), screenshot path/pattern, screenshot selection color, screenshot scale (real vs magnified), **OSD legend corner** (`osd_corner`, default `top-left`), **minimap corner** (`minimap_corner`, default `bottom-right`), and all keybindings including **Reset zoom** (`reset_zoom`, default `R`; MMB does the same), **Toggle magnified cursor** (`toggle_cursor`, default `C`), **Toggle minimap** (`minimap`, default `M`), the **Hold-to-zoom modifier** (`hold_to_zoom`, default `Super`), and **Toggle screenshot scale** (`screenshot_scale_toggle`, default `V`).
* **Animation timing:** `RawInput.time` is fed from a monotonic clock so egui animations (text caret blink) run at real speed instead of as-fast-as-frames-are-produced.
* **Factory Reset:** Per-setting reset buttons are *not* implemented (deferred); values can be reverted manually.
